# Build, check and artwork decisions

`S` is the skill's `scripts` folder. Keep the original extraction untouched; edit a working spec and retain a short decision log with the user's answers. All build filenames are new. A filename supplied for an existing output is rejected; do not delete the user's file to get around that check.

## Direct PPTX

```sh
osascript -l JavaScript "$S/powerpoint/build_check.js" <work>/deck-spec.json <new-output>.pptx [--width-in <confirmed-width>]
```

Google page properties in `spec.physicalSize` supply the original physical width automatically. A different width is rejected unless the user requested resizing and `--resize-approved` is supplied. Figma frames determine the aspect ratio. If the user says physical inches do not matter, `figma_to_spec.js --pixels-per-inch 96` supplies an explicit unit conversion; state the resulting dimensions and preserve the source ratio. Ask for physical dimensions only when needed.

Optional `--font-map '{"Source family":"Chosen family"}'` requires the user's agreed mapping. `--draft` is for visual review of reconstruction candidates while content is unresolved, not a finished conversion. The writer scales geometry, fonts, letter spacing, line heights, paragraph spacing, strokes and shadows consistently to the chosen physical size. It writes editable text/shapes and original image media into a PPTX; it does not open Keynote. PowerPoint uses Office family/style properties, including bold+italic together. Nonstandard installed weights use the face's human name and still require native checking. Missing exact styles are reported, never silently replaced by the nearest local face.

Inspect `skipped`, `unresolved_font_styles`, `unresolved_font_variations`, `fonts_not_installed`, `incomplete` and `errors`. Variable axes such as optical size remain unverified; retain their source values in the spec and ask about the unresolved match. Installed named faces can also render incorrectly in PowerPoint, particularly variable font weights. A native font mismatch requires the user's font choice even if the catalogue reported an exact installed face. Never fix it by silently choosing a different weight or installing another font version. `structural_valid` checks ZIP integrity, XML well-formedness, relationship targets, slide counts, dimensions and object counts; it is not Office schema validation or evidence that the file renders correctly. `native_render_verified` stays false at this stage. Any skipped/missing content blocks finished delivery even if a draft PPTX exists.

## Native render and visual review

Export every slide of the exact PPTX in PowerPoint using setup.md. Then:

```sh
osascript -l JavaScript "$S/powerpoint/check_render.js" <work>/deck-spec.json <output>.pptx <native-render-dir> --width 1920
```

The checker rejects an absent/mismatched manifest, stale PPTX hash, wrong slide count or missing native PNG. It compares source | PowerPoint | red difference at 1920 pixels across, preserving source aspect. It flags local differences, missing source references and low-quality references/renders. Contact sheets are previews; inspect the full-resolution individual comparisons for small text, thin strokes and shadows. Increase `--width` (up to 7680) when the user requests it and both exports support it; do not enlarge a low-resolution export and claim added fidelity. Check Google SVG references against the editor too: the live pilot exposed different wrapping between an outlined server export and the editor. Ask which source appearance to follow when they disagree; do not change editable text to match a different rendering without that decision.

Read `report.json` and look at **every** slide side-by-side, including slides with low scores. Check text content, line breaks, weight/italics, crop/mask/flip, stacking, effects and gradients. A numeric score is a pointer, not an acceptance decision. The script reports `visual_review_required:true` and `native_render_verified:false` because it cannot make that decision for the assistant. Record manual findings and remaining differences in `<work>/review.json`, along with renderer version/platform and the PPTX hash. Verify editing representative text, shapes and images in PowerPoint, and test GIF/video playback and clickable links in slideshow mode when present. No still image can prove playback or editability.

Fix conversion-caused offsets, wraps or effects in the working spec using the source as evidence. Do not introduce a new design to lower a score. Rebuild with a new name, export again and re-check affected slides. Final verification must cover every delivered slide and the exact final file. A changed PPTX invalidates earlier native renders; an old manifest is rejected. Show the pilot to the user and obtain their approval before the full batch.

## Complex artwork

Complex means the bundled representation cannot reproduce the source as editable elements with acceptable fidelity: examples are spread or multiple composited shadows, radial/angular gradients, blur, patterns, blend modes, complicated masks or complex paths. Difficulty alone does not authorize flattening. Linear gradients and simple shadows remain native candidates until checked. Existing photographs/image fills are already source images; retaining them is not a new artwork-flattening decision.

1. Identify the layer/frame id, source properties and unsupported behavior. Attempt a faithful editable reconstruction with shapes, vector paths, gradient fills, original image assets and shadows. For Figma, store arrays of replacement elements in `rebuilds.json`, keyed by node id or `frame-id:background`. Keep text separate and editable. An AI may construct any needed editable geometry; do not replace branded/source artwork with invented artwork without asking.
2. Build a review draft and compare the actual PowerPoint result with the source. Record the attempt, exact remaining difference, file hash and comparison path. A candidate existing in JSON is not a successful reconstruction. If native rendering is unavailable, the attempt has not passed or failed its required visual check: leave it unresolved, request the environment and do not jump to flattening.
3. On failure, show the comparison and ask whether to try again, use a picture for that identified artwork, or leave the issue unresolved. Explain exactly which elements become non-editable. The user can request more AI reconstruction attempts. Do not make fallback the default after an arbitrary retry count. Keep the attempt and approval log in `<work>/artwork-decisions.json`.
4. Only after that failed attempt and approval, export/download the isolated artwork. For Figma, save to `raster/<node-id-with-colons-as-hyphens>.png`; backgrounds use `raster/<frame-id>-background.png`. Preserve exported render bounds (including shadows) in `raster-bounds.json` as `{ "node-id": [x,y,w,h] }` relative to the frame. Ask separately if a backdrop effect requires baking nearby editable content into the image. Never use a whole-slide crop as an isolated background.
5. For an approved Figma background, run `scripts/create_background_artwork.js` through `use_figma`, prefixing `const FRAME_ID = '<id>';`. It creates only a temporary rectangle with the frame's fills/effects, without child text. Download that returned node's PNG at sufficient scale, save it as `<frame-id>-background.png`, record `renderBounds` from the helper in `raster-bounds.json` under `frame-id:background`, then immediately remove **only** the helper's returned `createdNodeIds`. Do not alter existing nodes. If export fails, clean up this job's temporary nodes before retrying.
6. Re-run `figma_to_spec.js <work> --target powerpoint --approved-rasters 'node-id,frame-id:background'` with exactly the approved IDs. A later request to try editable artwork again revokes that fallback for the element: remove it from the approval flag and create another candidate. Google Slides fallback is inserted into the working spec only for the named approved artwork, keeping its bounds and z-order; annotate `sourceId` and record it in `conversion.flattened_artwork`. Rebuild and check the fallback too.

Never declare full fidelity verified while unresolved artwork/assets/styles, unreviewed native differences or required playback checks remain. A user-approved choice to retain an unverified font match permits delivery with that specific exception clearly labelled; it does not establish a font match. Report the remaining limitations and provide a labelled draft when required checks cannot be completed.
